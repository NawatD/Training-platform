## หัวข้อที่ 1: LOS คืออะไร

```html
<p>LOS (Loan Origination System) คือระบบที่บริหารจัดการ "กระบวนการขอสินเชื่อทั้งหมด" ของธนาคาร ตั้งแต่ลูกค้ายื่นคำขอ ไปจนถึงเงินถูกโอนเข้าบัญชีลูกค้า (เบิกจ่าย) แล้วส่งต่อให้ระบบ Core Banking ดูแลการชำระคืนต่อไป</p>
<p>พูดง่ายๆ LOS เป็นเหมือน "สายพานการผลิตสินเชื่อ" — รับวัตถุดิบ (คำขอ + เอกสาร) เข้ามา ผ่านการตรวจสอบและอนุมัติหลายขั้นตอน แล้วส่งออกเป็น "สินเชื่อที่อนุมัติแล้ว" พร้อมเบิกจ่าย</p>
<div class="callout qa">
  <b>ทำไม QA ต้องเข้าใจ business ไม่ใช่แค่ทดสอบหน้าจอ</b><br>
  บั๊กที่อันตรายที่สุดในระบบสินเชื่อมักไม่ใช่ปุ่มกดพัง แต่เป็น "ตรรกะทางธุรกิจผิด" เช่น ระบบยอมอนุมัติให้คนที่ DSR เกินเกณฑ์ไปแล้ว หรือคำนวณค่างวดผิดเพราะสูตรดอกเบี้ยสลับประเภทกัน — ความผิดพลาดแบบนี้ทดสอบด้วยการคลิกผ่านหน้าจออย่างเดียวไม่เจอ ต้องเข้าใจ "กฎของธุรกิจ" เบื้องหลังก่อน ถึงจะออกแบบเทสเคสที่จับบั๊กจริงได้
</div>
<div class="term-grid">
  <div class="t">ชื่อเต็ม</div><div>Loan Origination System</div>
  <div class="t">หน้าที่หลัก</div><div>บริหารกระบวนการขอสินเชื่อ ตั้งแต่รับคำขอจนถึงเบิกจ่าย</div>
  <div class="t">ผู้ใช้งานหลัก</div><div>RM/พนักงานสาขา, Credit Analyst, ผู้อนุมัติสินเชื่อ, ฝ่ายเอกสาร/เบิกจ่าย</div>
  <div class="t">เชื่อมต่อกับ</div><div>Core Banking, เครดิตบูโร, ระบบ e-KYC, ระบบจัดเก็บเอกสาร (DMS)</div>
</div>
```

## หัวข้อที่ 5: Zoom in — วิเคราะห์เครดิต และการคำนวณ DSR

```html
<p>ขั้นตอนนี้ Credit Analyst จะดึงข้อมูลประวัติหนี้ของลูกค้าจากเครดิตบูโร แล้วประเมิน "ความสามารถในการผ่อนชำระ" ด้วยตัวชี้วัดหลักคือ DSR (Debt Service Ratio)</p>
<div class="callout">
  <b>สูตร DSR (Debt Service Ratio)</b><br>
  DSR (%) = (ภาระหนี้ที่ต้องผ่อนต่อเดือนทั้งหมด ÷ รายได้สุทธิต่อเดือน) × 100
</div>
<p><b>ตัวอย่างการคำนวณ</b></p>
<div class="term-grid">
  <div class="t">รายได้สุทธิต่อเดือน</div><div>80,000 บาท</div>
  <div class="t">หนี้เดิม</div><div>ผ่อนรถ 10,000 + บัตรเครดิต 5,000 = 15,000 บาท</div>
  <div class="t">ค่างวดสินเชื่อใหม่ที่ขอ</div><div>20,000 บาท</div>
  <div class="t">DSR</div><div>(15,000 + 20,000) ÷ 80,000 × 100 = <b>43.75%</b></div>
</div>
<p>ธนาคารส่วนใหญ่กำหนดเพดาน DSR ไว้ประมาณ 60–70% ของรายได้ (ตัวเลขจริงขึ้นกับนโยบายเครดิตของแต่ละธนาคารและประเภทสินเชื่อ) — ถ้า DSR เกินเพดาน ระบบควรปฏิเสธหรือส่งเรื่องให้พิจารณาเป็นกรณีพิเศษ ไม่ใช่อนุมัติผ่านอัตโนมัติ</p>
<div class="callout qa">
  <b>จุดที่ QA ควรเทส — Boundary case</b><br>
  DSR ที่คำนวณได้พอดีเท่าเพดาน (เช่น 70.00% พอดี) ต้องเทสว่าระบบตัดสินใจถูกต้องตามกฎ (ผ่านหรือไม่ผ่าน), DSR เกินเพดานเพียงเล็กน้อย (70.01%), กรณีไม่มีข้อมูลหนี้เดิมเลย, กรณีรายได้เป็น 0 หรือไม่มีข้อมูล, และการปัดเศษทศนิยมของ DSR ก่อนนำไปเทียบกับเพดาน (ปัดขึ้น/ปัดลง/ตัดทิ้งมีผลต่อผลอนุมัติหรือไม่)
</div>
```

```html
  <div class="t">ลดต้นลดดอก (Effective / Reducing Balance)</div><div>คิดดอกเบี้ยจาก "เงินต้นคงเหลือ" ในแต่ละงวด — นิยมใช้กับสินเชื่อบ้าน</div>
</div>
<p><b>ตัวอย่าง — ดอกเบี้ยคงที่ (Flat Rate)</b></p>
<div class="term-grid">
  <div class="t">เงินต้น</div><div>300,000 บาท</div>
  <div class="t">อัตราดอกเบี้ย</div><div>3% ต่อปี แบบคงที่ ผ่อน 3 ปี (36 งวด)</div>
  <div class="t">ดอกเบี้ยรวม</div><div>300,000 × 3% × 3 = 27,000 บาท</div>
  <div class="t">ค่างวดต่อเดือน</div><div>(300,000 + 27,000) ÷ 36 = 9,083.33 บาท (เท่ากันทุกเดือน)</div>
</div>
<p><b>หลักการ — ลดต้นลดดอก (Effective / Reducing Balance)</b></p>
<p>ค่างวดรายเดือนคงที่ตลอดสัญญา แต่สัดส่วนดอกเบี้ย/เงินต้นในแต่ละงวดไม่เท่ากัน — เดือนแรกๆ ดอกเบี้ยเยอะเพราะเงินต้นคงเหลือยังสูง ยิ่งผ่อนไปเรื่อยๆ เงินต้นคงเหลือลดลง ดอกเบี้ยของงวดถัดไปก็ลดลงตาม สูตรที่ QA ควรรู้เพื่อตรวจทานตัวเลขแต่ละงวด คือ:</p>
<div class="callout">
  ดอกเบี้ยของงวดนี้ = เงินต้นคงเหลือต้นงวด × อัตราดอกเบี้ยต่อปี ÷ 12<br>
  เงินต้นที่ตัดในงวดนี้ = ค่างวด − ดอกเบี้ยของงวดนี้<br>
  เงินต้นคงเหลือใหม่ = เงินต้นคงเหลือเดิม − เงินต้นที่ตัดในงวดนี้
</div>
<p><b>LTV (Loan-to-Value)</b> — ใช้กับสินเชื่อที่มีหลักประกัน เช่น บ้าน รถ</p>
<div class="callout">
  LTV (%) = วงเงินกู้ ÷ มูลค่าหลักประกัน (ราคาประเมิน) × 100<br>
  ตัวอย่าง: กู้ 2,400,000 บาท บ้านราคาประเมิน 3,000,000 บาท → LTV = 2,400,000 ÷ 3,000,000 × 100 = 80%
</div>
<div class="callout qa">
  <b>จุดที่ QA ควรเทส — Rounding</b><br>
  ทศนิยมของดอกเบี้ยแต่ละงวดปัดที่ตำแหน่งไหน (สตางค์), งวดสุดท้ายอาจต้องปรับยอดให้เงินต้นคงเหลือเป็น 0 พอดี (เก็บผลต่างจากการปัดเศษสะสมไว้ที่งวดสุดท้าย), จำนวนวันในเดือนไม่เท่ากัน (เดือนก.พ. 28/29 วัน) มีผลกับการคิดดอกเบี้ยแบบรายวันหรือไม่ — จุดเหล่านี้ผลต่างมักมีแค่ไม่กี่สตางค์ แต่สะสมทั้งพอร์ตอาจกลายเป็นปัญหาใหญ่
</div>
```

## หัวข้อที่ 8: Zoom in — เบิกจ่ายและส่งต่อ Core Banking

```html
<p>เมื่อคำขอได้รับอนุมัติแล้ว ขั้นตอนสุดท้ายคือจัดทำสัญญาเงินกู้ให้ลูกค้าเซ็นยืนยัน จากนั้นโอนเงินเข้าบัญชีลูกค้า (เบิกจ่าย) และส่งข้อมูลบัญชีสินเชื่อเข้าระบบ Core Banking (เรียกว่า "boarding") เพื่อให้ Core Banking ดูแลเรื่องการตั้งวันครบกำหนดชำระ คำนวณดอกเบี้ยรายเดือน และติดตามการผ่อนชำระต่อไป</p>
<div class="callout qa">
  <b>จุดที่ QA ควรเทส — ความเสี่ยงจากการเชื่อมต่อระบบ</b><br>
  ระบบ timeout หรือขาดการเชื่อมต่อระหว่างส่งข้อมูลไป Core Banking (ข้อมูลค้างอยู่ระหว่างระบบ สถานะไม่ตรงกัน), การเบิกจ่ายซ้ำ (double disbursement) ถ้ากลไก retry ไม่ทำแบบ idempotent, ข้อมูลไม่ตรงกันระหว่าง LOS กับ Core Banking เช่น อัตราดอกเบี้ยหรือวันครบกำหนดชำระที่ตกลงกันไว้กับที่ถูกตั้งค่าจริงในระบบปลายทาง
</div>
```
